# Audit complet — septembre 2026

Passe d'audit multi-agents (16 dimensions, un lecteur par dimension, vérification contradictoire par dimension quand disponible). Chaque constat cite un fichier et une ligne au moment de l'audit (commit `c53a3f8`). La colonne « État » est tenue à jour au fil des corrections.

Total : 382 constats.

## Domaine (16)

The domain package is small (~1,100 lines), pure, well-typed and pleasant: integer-minor Money with exact allocation (Fowler), branded ids, Result/DomainError for expected failures, aggregates that record events, and a clean fee-policy strategy. Money arithmetic, allocation sums, the Item transition table and the basic Sale/period/source computations are correct for the happy path and covered by 28 passing tests (typecheck clean). The weaknesses are in the economics the product is sold on: the default fee grid is stale or wrong for four of six platforms and its shape cannot express 2026 grids (tiers, processing fees, private vs pro); refunds and write-offs disappear from every report so profit is overstated; per-piece costs, source investment and sale snapshots can drift with no reconciling invariant; the "floor price" is a net figure presented as a listing price; and progressive detailing of a lot inflates that floor. Product-level gaps a reseller will hit quickly are multi-item/bundle sales, partial refunds, reservations with expiry and a fiscal regime (micro-BIC/TVA sur la marge). Tests pin the happy path only and re-implement formulas rather than assert golden values, and the package currently fails the repo's Biome gate (39 errors) which CI runs as a blocking step.

## Application (20)

The layer is well structured: every command is workspace-scoped through loadOwnedWorkspace, money enters only via readMoney (currency enforced, safe integers), transact() gives clean rollback-on-err semantics, quotas are centralised in ensureQuota/ensureFeature, and the in-memory adapters plus 43 focused tests make the use cases cheap to exercise (baseline: tests and typecheck green). The weaknesses are where the layer trusts its ports too much: the in-memory repositories return everything while the Drizzle repositories cap list() at 100 rows by default, so GetDashboard and ListSources compute revenue and source performance on truncated data in production. Cross-aggregate invariants are missing (an item can carry two open sales; the monthly source quota counts the UNIT sources it claims to exempt; currency can change once sources exist), quota checks for AI appraisals are not transactional, and events are published after commit through a non-transactional outbox. Several product-critical capabilities are absent from the layer entirely (members/MULTI_USER, CSV export, listing reprice/end, bulk status changes, cost re-allocation after receiving a lot), and idempotency lives as a compensating hack in the web route rather than in CreateItem, which can delete the winner's photo files.

## Infrastructure · base de données (20)

The persistence layer is well above MVP quality: every business table carries workspace_id with composite indexes, money is stored as bigint minor units plus a currency enum, enums are derived from the domain constants, upserts are guarded by `setWhere workspace_id = excluded.workspace_id`, the SKU counter is a single atomic UPDATE…RETURNING, the rate limiter is one atomic upsert, and a dedicated tenant-isolation test suite (110 tests, all green) proves cross-workspace reads and forged writes are no-ops. I verified with a drizzle-kit dry run into a scratch directory that the TypeScript schema and the three SQL migrations/snapshots are in sync, and that both the pg and PGlite drivers return `date` columns as strings so the mapping is driver-agnostic. The weaknesses are at the boundary between repositories and their callers: `list()` silently caps at 100 rows and the dashboard/source-performance code treats that page as the whole dataset (verified: 100 returned vs 1000 counted), cost-sorted pagination has no unique tiebreaker (verified: 8 rows missing and 1 duplicated across pages of tied rows), and deleting an item that has a cancelled sale surfaces a raw FK violation as a 500. Operationally, the documented `pnpm db:migrate` command points at a file that does not exist, the outbox and rate-limit purge are never scheduled so both tables grow without bound, and account deletion removes the workspace row but never cancels the Stripe subscription it referenced. CI only ever exercises PGlite, so real-Postgres behaviours (SSL, pooling, concurrent migrations) are untested.

## Infrastructure · adaptateurs (16)

The adapter layer is well above MVP quality in its own terms: 110/110 tests pass, typecheck and Biome are clean, the Stripe signature check is timing-safe with tolerance, the rate limiter is a single atomic upsert that is exactly correct under concurrency, photo keys are opaque UUIDv7 under a workspace prefix with a strict regex, and the AI router has a genuinely sound error taxonomy (retryable vs failover vs fatal) with typed SDK error mapping and a correct Fable 5.1 request shape (no thinking param, output_config.effort + zodOutputFormat, server-side fallbacks beta). What is weak is everything that only shows up against real services and real money: the Stripe integration has no guard against stale or out-of-order subscription events, Checkout can create a second subscription, and account deletion drops the workspace row without ever cancelling the Stripe subscription, so a deleted user keeps being billed. The R2 path signs an unbounded PUT, never verifies the object exists or is an image before attaching it, and skips the EXIF/GPS stripping that the local path does. AI spend is entirely unobserved (no usage capture, no cap on 'unlimited' plans, failed multi-provider attempts are free from the quota's point of view) on the most expensive model available. The outbox relay and rate-limit purge exist but nothing in the app, Dockerfile, Railway config or CI ever runs them. The prompt is a generic JSON-shape instruction rather than a reseller-grade appraisal rubric (no authenticity assessment, no condition-grade definitions, no target-margin/fee context, no date, a JPY hint bug).

## API web (22)

The HTTP layer is well-structured: every contract route has a handler, `withAuth`/`withPublic` uniformly enforce session, origin check on mutations, per-workspace rate limits with Retry-After, X-Request-Id and PII-free JSON logs, and bodies/queries are validated with the shared Zod contract while responses are checked against it outside production. Multi-tenant scoping is solid (every use case goes through `loadOwnedWorkspace`, photo keys are prefix-checked, the local photo route is path-safe). The weak spots are at the seams the framework helpers do not cover: the offline outbox's `X-Outbox-Id` header is sent but never honoured server-side, so replays after a timeout create duplicate PENDING sales/listings or wedge the sync queue; Better Auth is deployed without `trustedProxies`, which in 1.7.3 degrades multi-hop `X-Forwarded-For` requests into a single global sign-in bucket; AI provider failures bypass the `APPRAISAL_FAILED` mapping and surface as masked 500s while a 20 s client timeout lets abandoned appraisals still consume quota. Request-size limits exist only on the two raw-body routes (JSON bodies and R2 presigned uploads are unbounded), Stripe webhooks lack event idempotency/ordering, several multi-step handlers (PATCH item, settings, refund+restock) are non-atomic, and `GET /sources` full-scans items and sales on every call. Finally, the pricing page advertises "Export CSV" (even on Free) and "Accès API" but no route or token auth exists for either.

## PWA et hors ligne (18)

The offline layer is thoughtfully designed for the core "chiner sans réseau" flow: a Serwist SW with sensible custom API/image/font strategies and an /offline fallback, a Dexie outbox with sequential replay and clear status semantics, a separate pending-photo store that survives interrupted uploads, a persisted TanStack cache, and a server-side idempotent quick-capture keyed by clientId with a real conflict-resolution path. The UI surfaces state well (banner, badge, "Sync plus tard" pills, pending rows) and one Playwright scenario exercises the happy path. The weaknesses are in identity and lifecycle: nothing in the outbox, pending photos, persisted query cache or SW API cache is tied to the logged-in user, so a logout/login on the same device replays one account's mutations into another workspace and shows the previous account's data; sales/status replays are not idempotent server-side (the X-Outbox-Id header is sent but never read); app-shell/RSC caching is delegated to Serwist defaultCache with a 24h fixed expiry, so an installed app opened offline after a day lands on /offline; the SW uses skipWaiting with no update prompt; and failed entries have no inspect/discard UI. Timeouts, Background Sync, storage persistence and unit tests for the offline modules are all absent.

## Authentification et sécurité (26)

The foundations are genuinely solid: Better Auth is wired with Secure/HttpOnly/SameSite=Lax cookies and __Secure- prefix in HTTPS, trustedOrigins is set, a persistent atomic rate limiter backs both auth and API routes, API mutations get an Origin/Sec-Fetch-Site CSRF check with a test, env validation refuses production without a 32-char secret, security headers include HSTS preload, frame-ancestors 'none', nosniff and a Permissions-Policy, logs strip secret-looking keys and Sentry runs with sendDefaultPii=false, Stripe signatures are verified in constant time, and RGPD export/delete endpoints exist with tests. The weak spots are operational and product-level rather than cryptographic: account deletion never touches Stripe (a paying user keeps being billed), there is no self-service password recovery at all, client-side persistence (TanStack persister, service-worker cache, Dexie outbox) is neither user-scoped nor cleared at logout so shared devices leak and cross-post data, IP resolution behind proxies is inconsistent (spoofable first-hop in app code, collapsing to one shared bucket in Better Auth when X-Forwarded-For has two hops), JSON bodies are buffered without a size cap, CSP relies on 'unsafe-inline', the R2 upload path bypasses every server-side photo check and quota, and the privacy policy describes a product that differs from the code (CSV, 30-day deletion, truncated IPs, EU hosting). None of these require an architectural change; most are S/M fixes.

## Facturation, plans et tarifs (35)

The plumbing is solid: plan limits live in one domain module (`plans.ts`), quotas are enforced server-side in every creation path (CreateItem, GeneratePiecesForSource, createSourceInTx, AppraiseImage) inside transactions, the Stripe gateway uses signed webhooks with constant-time verification, the checkout return URL is origin-checked, and the no-Stripe mode degrades honestly (503, no fake redirect). Test coverage exists for the happy paths only.

## i18n et accessibilité (24)

The i18n core (packages/i18n) is well built: zero-dependency ICU-lite interpolation with real Intl plural rules, locale-correct EUR/date/percent formatting (verified fr-FR "1 284,50 €", en-GB "€1,284.50", de-DE "1.284,50 €"), typed keys, and FR≡EN parity enforced by tests. Most product screens correctly go through t()/useFormat(). The weak points are at the edges: DE is 88.6% missing (716/808 keys, appraisal and billing entirely absent) yet offered in the language picker; locale lives only in localStorage (no cookie, no Accept-Language, never hydrated from the workspace setting), so SSR always renders French and route-level chrome, the bottom navigation, the auth forms, the sync badge and every UI-package accessible name stay French for EN/DE users. Accessibility fundamentals are strong (focus-trapped modal Sheet, radiogroup/switch/slider semantics with keyboard support, aria-current tabs, reduced-motion honoured in both CSS and motion/react, thread focus ring at >4.6:1), but the Selvedge palette fails WCAG AA where it matters most: --ink-3 (form labels, placeholders, tab labels, subtitles) is 2.77:1 on calico, brass positive amounts are 3.95:1, input borders are 1.58:1, and dynamically-mounted live regions (toasts, sync badge) will not be announced reliably. No axe automation exists despite the readiness doc claiming AA.

## Design system (27)

packages/ui is a genuinely good foundation: a coherent brand language (Calico/Indigo palettes, three type voices, six named motion gestures), accessible primitives (Sheet with focus trap, Segmented radiogroup, TapeMeasure slider, SnapToggle switch, MoneyInput in minor units with French decimal parsing), reduced-motion handling on every motion component, and clean typecheck/biome/test runs (22 tests green). The weakness is that the app does not actually live on it: apps/web ships a second, CSS-class design system in a 2,389-line globals.css (.btn, .tag, .pill, .card, .seg, .tabbar, .topbar, .sk, .enter d1..d7) plus duplicate Icons/Stitch/Tally/TagMark/TabBar/TopBar components, so tokens drift (two --tabbar-h values, two easing names, colliding @keyframes that visibly break the ui Skeleton shimmer in the compiled CSS), and ui exports like riseIn/stagger/TopBar/TabBar/Logo have zero consumers. Concrete correctness gaps remain in the package itself: 15px form controls trigger iOS focus zoom, Button-as-link drops props, white-on-thread/indigo and --ink-3 fail contrast, hard-coded French strings inside a FR/EN/DE product, and sub-44px chips in the main edit form. The type/radius scales declared in tokens are unused (23 distinct arbitrary px sizes), the component API vocabulary (sizes/variants) is inconsistent enough that screens resort to !important overrides, and test coverage is shallow (no tests for ~15 components, reduced-motion paths never exercised, no tokens.ts/tokens.css parity check). For a launchable product the missing primitives are substantial: desktop data table and shell, date field, stepper, checkbox/radio, combobox with suggestions, banner/badge, and any chart primitive.

## Complétude produit (31)

The core loop is genuinely solid and better than most competitors' MVPs: four source kinds with cost allocation and floor price, a one-handed offline quick capture with geolocation, an item state machine with listings, a sale receipt with per-platform fee schedules, cancel/refund, RGPD export/delete, and a Stripe-backed plan model. Where it falls short is everything that turns a tracker into a business tool: the pricing page and plan table sell Premium/Pro/Business features (listing copy, advanced analytics + PDF, accounting export, QR labels, API access, team seats, custom branding) of which none is implemented and one (listing copy) is generated then discarded, so launching as-is would mean charging for absent features. Real reseller workflows are also half-covered: a brocante morning with 15 finds cannot carry its fuel/entry fees, a 48-piece Eureka pallet must be edited piece by piece, bundles and partial refunds do not exist, there is no expenses ledger or URSSAF/threshold view, no analytics beyond a headline margin, no reminders or notifications, and no CSV/spreadsheet import or export. Several half-done paths (PENDING sales without a completion route, sale edit route without UI, byPlatform stats computed but never rendered, historyMonths declared but not enforced) show the API got ahead of the screens. The domain is well shaped to absorb these additions; the main risk is marketing/plan promises diverging from shipped scope.

## Tests et qualité (24)

The test pyramid is unusually solid for a pre-launch product: 327 Vitest tests all pass (domain 28, application 43 on in-memory adapters with a FixedClock, infrastructure 110 on migrated PGlite including a rigorous multi-tenant isolation suite and AI-provider tests with recorded transports, contract 26, i18n 22, ui 22, web 76 route tests that exercise real handlers and validate every response against the contract Zod schemas via assertContract), type-safety is genuinely strict (no `as any`, no `@ts-ignore`, no non-null assertions, Biome errors enforced), and assertions are mostly behavioural (money in cents, HTTP codes, events). The weaknesses are structural rather than local: the CI lint gate is red today (126 Biome errors: the domain package was never formatted, docs/design HTML is linted), the whole client side of the PWA (hooks/api.ts, the Dexie outbox, pending photos, 30+ screens) has zero unit tests and is only exercised end-to-end against a 1 175-line hand-written fake API that does not import the contract, the single real-API journey silently `test.skip`s on a 5xx, and screenshots are captured but never compared. Business logic is triplicated (domain ScheduleFeePolicy/Sale.economics, web hooks/economics.ts, e2e fake-api feesFor) so the receipt the reseller sees before confirming a sale is computed by untested code; several use cases (CompletePendingSale, SimulatePrice, UploadPhotoBytes) and hooks (useUpdateSale) are wired to nothing, and `pnpm db:migrate` points to a file that does not exist. Concurrency-sensitive code (SKU sequence, rate limiter) is only proven on single-connection PGlite; there is no real Postgres, no drizzle drift gate, no coverage measurement and no axe pass anywhere in CI. Recommended plan, in order: (1) day 1 — run `biome check --write`, exclude docs/design, fix db:migrate path, replace the e2e `test.skip` with a hard failure, tighten the four loose assertions; (2) week 1 — add a jsdom Vitest project in apps/web with testing-library + fake-indexeddb and cover outbox/pending-photos replay, optimisticStatus/localSale and NewSale/Chiner flows, add route tests for /appraisals, delete hooks/economics.ts in favour of @chine/domain and make fake-api validate with the contract schemas; (3) week 2 — Postgres service + drizzle-kit check in verify.yml, split screenshots.spec into per-screen tests with toHaveScreenshot baselines and no sleeps, add @axe-core/playwright on the six screens, install @vitest/coverage-v8 with thresholds, and adopt knip to keep dead exports out.
